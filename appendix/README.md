10.0 Appendix A: Technical Configuration and Test Details
This appendix provides the technical configuration and test information used to implement and validate the experimental environment. It is included to support reproducibility, transparency and verification of the practical evaluation presented in the research.

10.1 Virtual Machine Configuration
The research was conducted within a controlled virtual laboratory using VirtualBox. The laboratory consisted of the following principal components:
Component	Role	IP Address
Kali Linux	Attacker/Test Host	192.168.1.113
Windows 11 Professional	Protected Endpoint	192.168.1.111
Ubuntu Desktop	Snort IDS Host	192.168.1.110
pfSense	UTM/Default Gateway/DHCP	192.168.1.1
The laboratory used the 192.168.1.0/24 network.
pfSense provided DHCP services and gateway functionality for the laboratory network.
The virtual environment allowed the experiments to be conducted in a controlled and repeatable manner without affecting external systems.

10.2 Kali Linux Configuration
Kali Linux was configured as the controlled attacker and network-testing host.
Role: Attacker / Security Testing Host
IP address: 192.168.1.113
Network: 192.168.1.0/24
Gateway: 192.168.1.1
Kali was used to perform controlled reconnaissance and traffic-generation activities against the Windows endpoint.
Examples of testing activities included:
•	ICMP connectivity testing. 
•	Network reconnaissance. 
•	TCP port scanning. 
•	Controlled traffic generation for Snort detection. 
•	HTTPS connectivity testing for pfSense filtering. 
The testing activities were conducted exclusively within the isolated research laboratory.

10.3 Windows 11 Configuration
The Windows 11 Professional virtual machine represented the protected enterprise endpoint.
Role: Protected Windows Endpoint
IP address: 192.168.1.111
Network: 192.168.1.0/24
Gateway: 192.168.1.1
Windows Defender Firewall was enabled and configured with controlled inbound rules.
Trusted security infrastructure was permitted where required, including:
•	192.168.1.1 — pfSense gateway 
•	192.168.1.110 — Snort IDS host 
Traffic originating from the Kali testing host (192.168.1.113) was not included in the trusted sources for the relevant endpoint firewall rules.
This configuration allowed the research to evaluate the ability of Windows Defender Firewall to distinguish between authorised and unauthorised traffic.

10.4 Snort IDS Installation and Configuration
Snort was deployed on the Ubuntu Desktop virtual machine.
Role: Network Intrusion Detection System
IP address: 192.168.1.110
Monitoring interface: enp0s8

Snort was started using:
sudo snort \
-i enp0s8 \
-c /usr/local/etc/snort/snort.lua \
-A alert_fast
The enp0s8 interface was used as the monitoring interface.
A custom ICMP detection rule was created for Scenario 5:
alert icmp 192.168.1.113 any -> 192.168.1.111 any (msg:"SCENARIO 5 - ICMP activity from Kali to Windows"; sid:1000001; rev:1;)
The rule was designed to detect ICMP activity originating from Kali and directed towards the Windows endpoint.
During the successful test, four ICMP Echo Requests generated by Kali resulted in four corresponding Snort alerts.

10.5 pfSense UTM Installation and Configuration
pfSense was deployed as the network gateway and UTM security platform.
Role: UTM / Firewall / Default Gateway / DHCP Server
LAN IP: 192.168.1.1
Network: 192.168.1.0/24
pfSense provided DHCP services to the laboratory hosts and acted as the default gateway.
The platform was used to evaluate network-level traffic filtering and blocking. The primary Scenario 6 test involved blocking HTTPS traffic originating from Kali.



The relevant firewall policy was configured as:
Parameter	Value
Action	Block
Source	192.168.1.113
Destination	Any
Protocol	TCP
Destination Port	443
The rule successfully prevented Kali from accessing HTTPS services through the pfSense gateway.

10.8 Snort Alerts and Logs
During Scenario 5, Snort successfully generated alerts for the ICMP traffic generated by Kali.
The successful experiment produced four alerts corresponding to four ICMP Echo Requests:
[1:1000001:1] "SCENARIO 5 - ICMP activity from Kali to Windows" {ICMP} 192.168.1.113 -> 192.168.1.111
The four alerts confirmed that:
1.	Kali generated the test traffic. 
2.	The traffic was visible to the Snort monitoring interface. 
3.	Snort successfully matched the configured detection rule. 
4.	Snort generated an alert for each detected ICMP packet. 
These alerts constitute the primary evidence supporting the Scenario 5 results.

10.9 pfSense Logs and Evidence
The pfSense experiment provided evidence of gateway-level traffic enforcement.
The Scenario 6 firewall policy targeted:
Source:           192.168.1.113
Protocol:         TCP
Destination Port: 443
Action:            BLOCK
When the rule was enabled, Kali was prevented from establishing HTTPS connectivity through the pfSense gateway.
The rule was subsequently disabled and the relevant firewall state cleared, after which connectivity was restored.
The pfSense firewall configuration, blocked-traffic entries and before/after connectivity results should be retained as experimental evidence alongside screenshots of the relevant firewall configuration and logs.
This evidence supports the conclusion that the observed HTTPS disruption was attributable to the pfSense firewall policy and demonstrates its effectiveness as a gateway-level traffic enforcement control.
